# Запуск DuelBattle в продакшене

## 1. Подготовь сервер и домен

Нужен Linux-сервер с Docker Engine и Docker Compose v2, постоянным диском и открытыми входящими портами **80 и 443**. Создай DNS-запись A домена на IP сервера. Если есть AAAA, она тоже должна вести на этот сервер.

Начни с одного экземпляра приложения. Одновременные комнаты держатся в памяти; перезапуск прерывает текущие игры. SQLite, аккаунты и законченные матчи остаются на постоянном томе. Не включай автоматическое масштабирование до нескольких экземпляров.

## 2. Загрузи код и настройки

Перенеси репозиторий без `node_modules`, локальных баз, `.env` и временных файлов. В папке проекта на сервере:

```sh
cp .env.example .env
```

Открой `.env` и укажи:

```dotenv
DOMAIN=game.example.com
GEMINI_API_KEYS=
GEMINI_MODEL=gemini-2.5-flash
MAX_ROOMS=100
```

Замени домен своим. Значение DOMAIN не должно содержать `https://`, путь или порт. AI-ключ можно оставить пустым: рейтинговые задания тогда проверяются камерой. Если включаешь Gemini, впиши серверный ключ и доступную твоему аккаунту модель, настрой бюджет в кабинете провайдера. На один AI-раунд приходится минимум две проверки, а не один запрос.

Не добавляй ключи в `VITE_*` и не публикуй `.env`. Compose сам задаёт production-режим, разрешённый Origin и безопасные cookies. Порт приложения не публикуется наружу; доступ идёт через Caddy.

## 3. Собери и запусти

Для регистрации настрой Google OAuth и отправку кодов на почту по
[инструкции аккаунтов](ACCOUNTS-AND-ITEMS.md). Compose передаёт эти переменные серверу.
Без почтового сервиса новая email-регистрация в production недоступна.

```sh
docker compose up -d --build
docker compose ps
docker compose logs --tail=80 game proxy
```

Caddy получает HTTPS-сертификат для домена автоматически. Для этого DNS должен уже указывать на сервер, а порты 80/443 должны быть доступны. Статус контейнера `game` должен быть `healthy`.

Убедись, что диск с Docker volumes постоянный. Том `game-data` содержит `battle.sqlite` и `identity.key`. **Не выполняй `docker compose down -v`**, если данные нужно сохранить.

При переходе со старой версии сначала сохрани её данные. Новый сервер импортирует прежний `profiles.json` только при первой инициализации соответствующего DATA_DIR. Для сохранения старых подписанных профилей нужен и прежний `identity.key`. Не подмешивай старые файлы в уже запущенную новую базу; перенос делается до первого запуска или через подготовленную резервную копию.

## 4. Проверь опубликованный адрес

```sh
curl -fsS https://game.example.com/healthz
curl -fsS https://game.example.com/readyz
```

Первый адрес должен вернуть `{"ok":true}`, второй — `{"ready":true}`. `/readyz` дополнительно проверяет соединение с базой.

Затем на двух устройствах сделай один короткий ручной проход:

1. Войди через Google или создай аккаунт с подтверждением почты, выйди и войди снова.
2. Открой обычную игру или комнату с другом. Разреши камеру, сыграй матч, нажми реванш. Проверь музыку внутри игры и выключение общим значком звука.
3. Проверь русский/английский и светлую/тёмную темы на телефоне.
4. Сыграй рейтинговый матч: проверь историю, рейтинг, опыт и Battle коины. Купи доступный предмет и надень его в профиле. После пяти зачётных матчей игрок появляется в таблице лидеров.
5. Если подключён AI, отдельно проверь реальный снимок и ситуацию недоступного провайдера. При неудачной проверке рейтинг и опыт не должны меняться.

На удалённом HTTP камера и production-cookie не заработают: используй именно HTTPS. Локальная сборка не заменяет проверку камер, реального AI и сети на опубликованном домене. Браузерная проверка последней итерации и реальный платный AI здесь не запускались по твоей просьбе.

До публичного набора игроков добавь контакты поддержки и подходящую твоему сервису политику приватности, укажи выбранного AI-провайдера. Игра передаёт фото сопернику, а при AI-проверке — также этому провайдеру.

## 5. Настрой резервные копии

Нельзя просто копировать один живой `battle.sqlite`, игнорируя WAL. В проекте есть команда для согласованного снимка базы:

```sh
mkdir -p backups
stamp=$(date -u +%Y%m%dT%H%M%SZ)
docker compose exec -T game node packages/server/scripts/backup.mjs /app/data /tmp/backup-$stamp.sqlite
docker compose cp game:/tmp/backup-$stamp.sqlite ./backups/battle-$stamp.sqlite
docker compose cp game:/app/data/identity.key ./backups/identity-$stamp.key
chmod 600 ./backups/*
docker compose exec -T game rm /tmp/backup-$stamp.sqlite
```

Если IDENTITY_SECRET задан внешним секретом, сохрани его в защищённом хранилище вместо файла identity.key. В базу входят аккаунты, хеши паролей и активных сессий: резервная копия тоже приватная.

Запланируй ежедневное выполнение у своего хостера и копирование на другой сервер или в закрытое хранилище. Периодически проверяй восстановление в отдельном DATA_DIR. Для восстановления останови игру, замени базу снимком и верни соответствующий ключ; старые `-wal` и `-shm` не должны смешиваться с восстановленной базой. Права файлов должны позволять пользователю контейнера `node` читать и писать их.

## 6. Обновляй с возможностью отката

Сначала сделай резервную копию и сохрани предыдущий образ или ревизию. Предупреди игроков о перерыве: активные матчи пока не восстанавливаются после перезапуска.

```sh
docker compose build game
docker compose up -d game
docker compose ps
curl -fsS https://game.example.com/readyz
```

Не удаляй том. При обновлениях с изменением схемы БД старой версии приложения может потребоваться восстановленная предобновлённая база, а не только старый образ.

## Если запускаешь без Docker

Нужен Node.js 24+, постоянный DATA_DIR, менеджер процесса и HTTPS-прокси с поддержкой WebSocket. После `npm ci && npm run build` запусти `npm start` со следующими переменными:

```dotenv
NODE_ENV=production
DATA_DIR=/absolute/private/path/duelbattle
CLIENT_DIR=/absolute/path/to/repo/packages/client/dist
HOST=127.0.0.1
PORT=8787
ALLOWED_ORIGINS=https://game.example.com
TRUST_PROXY=1
```

TRUST_PROXY=1 допустим только когда к серверу обращается твой доверенный прокси, который переписывает X-Forwarded-For. Наружу должен смотреть HTTPS-прокси, а не порт 8787. Клиент, auth API и WebSocket должны быть на одном публичном origin.

## Что наблюдать после запуска

- Доступность `/readyz`, перезапуски процесса, свободный диск и память.
- Серверные JSON-логи ошибок матчей, SQLite и AI; никаких фото, паролей и ключей в логах.
- Время ожидания соперника и AI, расходы провайдера, долю нейтральных результатов.
- Резервные копии и срок действия HTTPS-сертификата.

Это конфигурация для одного сервера. Нагрузочный тест, Docker/HTTPS на выбранном хостинге и живой AI в этой итерации не проверялись. Не считай MAX_ROOMS гарантированной пропускной способностью: выбирай лимит по фактической памяти, CPU и каналу сервера.
